## Project overview

**Goal:** Submit Prove It to the Flip the Switch hackathon's Track 01, Best Business Workflow. Prove It helps maintainers triage security reports: a reporter submits a claim in Switch, Intake requests a data-only proof, a sandbox records what happened, a Reproducer and Skeptic examine the evidence, and a human maintainer decides. The result returns to the reporter's thread. The intended users are open-source maintainers and teams handling public vulnerability reports.

**Why this project:** AI-generated, low-quality reports consume maintainer time. The team chose a workflow that asks the reporter for reproducible evidence, keeps Switch central to coordination, and keeps the final decision with a person. The [README](README.md) explains the product and limits; [SETUP](docs/SETUP.md) is the operational guide; [DEMO](docs/DEMO.md) is the current walkthrough.

**Hackathon scope:** A reproducible Switch workflow for the four supplied report replays, with an honest distinction between real, synthetic, and unverified results. This file tracks the hackathon through submission, not a post-hackathon product roadmap.

## Architecture and rules

- `proveit/intake.py` is a Python Switch agent, not an LLM. It handles the public intake room and routes fixed-field tickets to triage. `proveit/switch_client.py` implements its Switch connection.
- `#proveit-intake` holds reporter threads; `#proveit-triage` holds maintainers and the Reproducer (Claude Code) and Skeptic (Codex). The rooms are linked by the `triage` link in [the Switch template](switch/prove-it.template.yaml).
- `proveit/poc.py`, `proveit/sandbox.py`, and `target/` validate and run one allowlisted PyYAML entry point on a YAML payload in a restricted Docker container. The parent process observes the child and writes the outcome.
- `proveit/states.py`, `proveit/actions.py`, and `proveit/messages.py` enforce state changes and human decisions. `proveit/evidence.py` provides the evidence pack.
- Python 3.9+ and Docker are required to run the project. The demo targets Switch 0.31.0 and PyYAML 5.3.1 (vulnerable) versus 5.4 (patched). See the README for tested environments and exact commands.

The following rules govern all hackathon work:

1. A reporter's proof is data: an allowlisted entry point plus a UTF-8 YAML payload no larger than 64 KB. Do not accept reporter-supplied Python or unsafe loaders.
2. Agent-visible tickets, messages, output, and evidence contain fixed or sanitized fields. Reporter prose and raw payloads stay in private storage; agents must not read them.
3. Only a human maintainer may escalate, close, release, or override a report. A quarantined report cannot be escalated; a dispute requires a human override before escalation.
4. A result must say what was actually observed. A headless run with scripted agent choices does not verify live Claude Code or Codex behavior. Switch Trust was verified live on 2026-11-06 with the Regex-only policy in SETUP §5; do not claim more than that policy does.
5. Keep **Bypass permissions** off for the two command-running agents in Switch Console. Their folders in `agents/` carry scoped permissions.

## Key decisions

These records are authoritative. Keep their IDs and reasons when updating them; refer to an ID elsewhere instead of copying its record.

- **D-001 — Build Prove It for Track 01.** Reason: the team judged it a more distinctive, Switch-centered, and achievable hackathon workflow than Shipyard or API Change Gate. Source: former `docs/team-brief.md` at commit `de6b7a6`.
- **D-002 — Accept data-only YAML proofs.** Reason: the original reporter-supplied Python could forge a result and manufacture crash or resource-exhaustion outcomes. A limited entry point and payload remove those arbitrary actions. Source: audit redesign in commits `302ea3f` and [blog draft](docs/blog-draft.md#the-hole-a-proof-that-grades-itself).
- **D-003 — Have a separate parent observe the proof process.** Reason: the first harness shared a process with untrusted code, allowing the code to read or forge the result; the parent now makes the classification from its own observations. Source: `302ea3f`, with a forged-MemoryError correction in `c1b36bb`.
- **D-004 — Show agents fixed-field evidence, never reporter prose.** Reason: the audit found reporter text in titles, excerpts, and exceptions, creating a prompt-injection path. Source: `9370c8e` and [blog draft](docs/blog-draft.md#agents-get-evidence-never-prose).
- **D-005 — Keep final report decisions with maintainers.** Reason: agents should test and challenge evidence while a person decides whether to escalate or close. Source: `9370c8e`, [README: Ticket states](README.md#ticket-states).
- **D-006 — Use one root context file plus a short agent entry point during the hackathon.** Reason: people and agents need the same current status and selective history, with one obvious place to update it. Source: team answers on 2026-11-05.
- **D-010 — Switch Trust policy: Regex patterns only, Block, User role; no Jailbreak, Secrets, PII or Redact.** Reason: in the live test Jailbreak also blocked report 02's proof, because a proof describes an attack. Redaction would change a payload and its SHA-256. Agents never see reporter text, so the other detectors add nothing. (D-007 to D-009 are recorded in docs/CHECKPOINT.md.) Source: [Trust log](docs/evidence/live-trust-2026-11-06-windows.log), 2026-11-06.
- **D-011 — Every check runs the payload 3 times, one after another, each in a new container (`CHECK_RUNS` in `proveit/config.py`).** Reason: a single run can be an artefact of the run itself ("Reproduce N times from clean state", proposed in OpenSSF issue #178). The runs are sequential because parallel runs compete for memory and CPU, which would make resource-exhaustion results unreliable. On the demo machine, 3 runs add about 1.3 to 1.4 s to a normal check (under the 15 s limit set for this change); the worst case, a payload that hits the 10 s call limit, takes about 32 s instead of 11 s. The setting is not an environment variable, so an agent cannot lower it. If Docker cannot start a run, the whole check is abandoned and nothing is recorded. Source: `scripts/time_checks.py`, 2026-11-07.
- **D-012 — If a check's runs disagree, it records `NOT_RELIABLY_REPRODUCED`, and escalation needs a maintainer's override.** Reason: a result that happens only sometimes is not proof, but it is not a clean negative either. A Skeptic's concur is not enough; a person must decide. One override lifts every block on the ticket (a dispute and the disagreeing runs), and the override records what it lifted. Source: `tests/test_repeats.py`, 2026-11-07.
- **D-013 — A dispute carries exactly one reason code from `proveit/reasons.py`; free-text disputes are refused.** The codes: `not_reproduced`, `not_clean_reproducible`, `also_on_patched`, `out_of_scope_api`, `outcome_mismatch`, `severity_overclaimed`, `version_missing`, `patched_not_checked`. Reason: a shared rejection vocabulary with "the one question that resolves it" (proposed in OpenSSF issue #178; the working group's draft has a templated rejection naming "the specific missing element"). Code decides: Intake refuses `not_reproduced`, `not_clean_reproducible`, `also_on_patched` and `patched_not_checked` when the recorded evidence contradicts them; the other codes are the Skeptic's judgement. The Skeptic's note stays in triage. There is deliberately no fallback for free text, so the live Skeptic needs the new instructions. Source: `tests/test_reasons.py`, 2026-11-07.
- **D-014 — The reporter gets at most one fixed question, only when a maintainer closes the ticket.** Order:
  1. `close R-NNN reason=<code>`;
  2. else the latest dispute's code, if it still stands (not overridden) and has a question;
  3. else the code the evidence implies (`NOT_REPRODUCED` gives `not_reproduced`, `NOT_RELIABLY_REPRODUCED` gives `not_clean_reproducible`; never for information-leak claims);
  4. else no question.

  `also_on_patched` and `patched_not_checked` never produce a question. A maintainer may close a ticket whose standing dispute is `also_on_patched` without an override, but must add a note, and the reporter gets no question. Questions are filled only from closed lists and config. Reason: no agent text ever reaches a reporter, and a question at dispute time would reach reporters before a human decided. Source: `tests/test_reasons.py`, 2026-11-07.
- **D-015 — A written scope policy ([docs/policy/pyyaml-scope.md](docs/policy/pyyaml-scope.md)), enforced at Intake.** `unsafe_load`, `unsafe_load_all`, and `load` with `UnsafeLoader` or `Loader` are out of scope; PyYAML documents them as unsafe for untrusted input. Intake answers with fixed text naming the entry point by its canonical name, and the proof never reaches the sandbox. Reason: the OpenSSF working group's draft calls a published threat model "one of the highest-leverage investments a project can make", and enforcing it in code means no agent or maintainer has to argue it. The Skeptic gets the same policy as a room doc, because its shell may not read files. Source: `tests/test_scope.py`, 2026-11-07.
- **D-016 — The proof request asks for four fields; `affected_version` is required.** The request lists `affected_version`, `entry_point`, `payload` and `expected`/`actual`, with an example. Without a version (or with text that is not a version) Intake asks again with fixed text and the report does not reach triage. The version is stored normalized (`5.3.1`, `<5.4`, `before 5.4`). Only the pinned builds ever run, and the ticket shows "reported: X, tested: 5.3.1". `expected` and `actual` stay in the private report and never reach agents. `version_missing` remains the Skeptic's backup code. Reason: the working group's draft asks for "exact, reproducible steps … including version", and a comment on #178 suggests capturing "which affected-version … fields a report states up front". Source: `tests/test_report_fields.py`; CVE-2020-14343's affected range from NVD ("versions before 5.4"), 2026-11-07.
- **D-017 — A successful `escalate` writes a DRAFT advisory pack; it claims no fixed version and holds no payload.** `work/R-NNN/advisory/` holds `osv-draft.json`, `ghsa-draft.md`, `timeline.md` and `timeline.json`, written atomically with LF endings and included in the export's manifest. A close or a refused escalate writes nothing. The OSV ID is `x_DRAFT-PROVEIT-R-NNN`: the prompt's `DRAFT-PROVEIT-R-NNN` fails the official schema, which requires a registered prefix or `x_` ("a local database that isn't aggregated by OSV.dev"); the team chose `x_` on 2026-11-07. `versions` lists only the exact build the sandbox saw reproduce; `not_reproduced_on` appears only when the patched check recorded NOT_REPRODUCED; a CVE alias only when the maintainer's escalate note contains one. The payload is named by hash, size and known tags, and the private copy by a relative path, because `work/` is agent-readable (rule 2, D-004). Reason: a maintainer gets a reviewable draft and a timestamped trail from recorded data only, without Prove It asserting a fix it never tested. Source: `tests/test_advisory.py`, `tests/data/README.md` (osv-schema v1.9.2, Apache-2.0), 2026-11-07.
- **D-018 — A proof record per reporter, by HMAC, outcomes only; at 2 failures, one open report at a time.** `reporters.json` in the private folder maps HMAC-SHA256(secret, the Switch participant id `sender`, or `sender_name` when a message has none) to good and invalid counts and timestamps, plus `id_source` (the field's name, never its value). The secret is random, made on first use in the private folder. Invalid means a close as `NOT_REPRODUCED` or `NOT_RELIABLY_REPRODUCED` (not information-leak claims) or a proof Intake rejected, at most once per ticket. Good means an escalate. Nothing else counts. At `INVALID_THRESHOLD` (2), a reporter who already has an open report (in triage or waiting for a proof; quarantined does not count) cannot open another; the new text is not stored. `clear-reporter` (maintainers only) lifts it. Reason: the working group's draft says to manage repeat submitters and raise "signal requirements", and the issue lists "Banning repeat offenders" as under discussion. This slows a repeat sender without banning anyone and without judging text. Replays all post as one reporter, so the rehearsal reaches the threshold after R-002 and R-003; its step 6 shows the limit and `clear-reporter` on purpose rather than hiding it. Source: `tests/test_reputation.py`, 2026-11-07.
- **D-019 — One target adapter.** Everything library-specific — name, pinned builds and images, allowlisted entry points, out-of-scope names, payload format, scope-doc path, proof-request text, rooms, and the per-library entry-point parser and tagger — is reached through a `Target` (`proveit/targets.py`); the sandbox, Intake, messages, evidence and advisory take a target, never a library name. Reason: a second library must reuse the same harness and agents, which needs one seam instead of scattered PyYAML literals. The PyYAML target delegates to the existing `config`/`poc` values (the same objects), so PyYAML's behaviour is unchanged — proven by an unchanged test suite and rehearsal digest. Source: `tests/test_targets.py` (pins the PyYAML harness hash `9b1b9e654cc0f147`), commit on branch `feat/second-library`, 2026-11-07.
- **D-020 — A second target gets its own `target-<lib>/`; `target/` stays byte-identical.** The shared, reusable part is the Python adapter interface in `proveit/`, not the sandbox image. `target-sqlparse/` has its own Dockerfile and image tags; its `harness.py` and `child.py` are copies of `target/`'s with a header naming the copy and its one library-specific difference. Reason: editing `target/` would rebuild the live PyYAML images (shared by every checkout on the machine) and break the pinned harness hash; a separate folder keeps the live demo untouched. Source: `tests/test_targets.py`, `target-sqlparse/`, 2026-11-07.
- **D-021 — Intake picks a report's target from the room it arrived in, never from the reporter's text; ticket ids stay one global sequence; a bare `proveit build` builds PyYAML only.** Each room pair's callbacks are bound to that room's target; the ticket records its target (`record["target"]`), and a ticket with no such field means PyYAML, so live tickets are unaffected. A second target's images are built only by `proveit build --target <lib>` and never auto-built, so the test suite never builds one. Reason: the room is the trustworthy signal for which library a report is about; reporter text is untrusted. `doctor` reports a missing second-target image as a WARN, not a FAIL. Source: `tests/test_rooms.py`, `tests/test_second_target.py`, 2026-11-07.
- **D-022 — A maintainer may decide a ticket from either triage room; cross-room commands are accepted, not refused.** A command is matched to its ticket by id regardless of which triage room it came from; the acknowledgement lands in the room the maintainer used, and the reporter is always told in the ticket's own intake room. Reason: humans rule — code may refuse an agent but must never stop a maintainer from deciding, and a maintainer should not be blocked for typing in the "wrong" room. One maintainer list governs every room (per-room maintainers are future work); this is a visible change from the single-room design. Source: `tests/test_rooms.py`, 2026-11-07.
- **D-023 — The second target is sqlparse, CVE-2023-30608 (ReDoS), with an empty out-of-scope list.** A 43-byte SQL payload (a quote then 42 backslashes, no closing quote) through the documented `sqlparse.parse` recorded RESOURCE_EXHAUSTION 3/3 on 0.4.3 and NOT_REPRODUCED 3/3 on 0.4.4, in a container with the same flags and limits as PyYAML. sqlparse documents nothing as unsafe for untrusted input, so unlike PyYAML its out-of-scope entry-point list is empty: a report naming an internal module (`sqlparse.lexer`, `sqlparse.engine.*`) is refused as "not an allowed entry point", never as "out of scope". Reason: the brief needs a public CVE whose PoC is a text input to a documented entry point, reproducing offline on a pinned pair; sqlparse's ReDoS fits and its outcome class (RESOURCE_EXHAUSTION) is one the judge already knows. Source: `docs/policy/sqlparse-scope.md`, `tests/test_second_target.py`, NVD CVE-2023-30608 (CVSS 7.5), GHSA-rrm6-wvj7-cwh2, 2026-11-07.

- **D-024 — Resume committed delivery and advisory work; bind agent verdicts to the evidence read.** Delivery receipts and pending decision effects survive restarts; a failed triage acknowledgement cannot prevent reporter notification. The same platform decision message is idempotent. HTTP acknowledgement loss can still duplicate a post (at least once, not exactly once). Agent room verdicts must carry the review token copied from the evidence pack; a changed token is refused under the ticket lock. Late checks are kept in `late_runs` without changing a terminal decision's evidence. Reason: preserve work through failures and avoid approving a run the Skeptic never inspected. Sources: `tests/test_fix_pass.py`, `tests/test_targets.py`, 2026-11-07.

- **D-025 — Verify the second branch in isolated trial rooms and commit one logical change at a time.** Generated trial names, settings, credentials and ticket/private paths are separate from the working demo; its linked triage names are checked before serving them. Preserve the existing provider lockdowns. Reason: a failed live trial must not displace the working workflow, and a published regression can be undone with a normal revert. Source: user instruction on 2026-11-07, `tests/test_trial.py`, [trial guide](docs/TRIAL.md). Live behavior remains unverified until recorded.
- **D-026 — An agent's folder, not its environment, decides how `python -m proveit` is found and which role it runs as.** Reason: on 2026-11-07 the Switch-managed Skeptic's session did not apply `PYTHONPATH` from its Codex config, so it could not import the project, and the same missing variables would have left its shell with a human's permissions. Source: `agents/*/proveit/__init__.py`, `tests/test_agent_folders.py`.
